<p class="eyebrow">MODULE 04 · ADVANCED FIELD ENGINEERING</p><p>Harbor’s identity team has resolved the scope regression from Chapter 17. Now the security reviewer asks a broader question: “How do we know that a signed-in coordinator can only access the records and actions they should?” A working login and an encrypted connection are useful controls, but neither answers that authorization question.</p><p>This chapter turns security requirements into explicit policy, data-flow decisions, and review evidence. Harbor and the examples are fictional. The authorization lab is a local teaching model, not a production policy engine or a security certification.</p><div class="lesson-panel"><h3>Learning objectives</h3><ul><li>Distinguish identity, authentication, authorization, and audit.</li><li>Define permissions for users, services, records, and actions.</li><li>Trace sensitive data through storage, exports, logs, and support workflows.</li><li>Plan credential lifecycle and access revocation.</li><li>Prepare a security review with concrete positive and negative tests.</li></ul><p>Allow 100–130 minutes including practice. Prerequisites: Chapters 12, 13, and 17. Produce an access matrix, data-flow inventory, and security evidence packet.</p></div>
<h2 id="section-1">18.1 Four questions that must stay separate</h2><div class="table-wrap"><table><thead><tr><th>Concern</th><th>Question</th><th>Harbor example</th></tr></thead><tbody><tr><td>Identity</td><td>Which principal is this?</td><td>A coordinator or an ingestion service.</td></tr><tr><td>Authentication</td><td>How was the claimed identity established?</td><td>An approved identity-provider flow or workload credential.</td></tr><tr><td>Authorization</td><td>May this principal perform this action on this resource now?</td><td>Read a particular warehouse’s exception evidence.</td></tr><tr><td>Audit</td><td>Can an authorized reviewer reconstruct relevant actions?</td><td>Actor, target, action, outcome, and time recorded with controlled access.</td></tr></tbody></table></div><p>A valid session does not grant access to every record. An API scope may permit a class of operation while a record-level policy still restricts the warehouse. An audit event records a decision; it does not make an incorrect decision safe.</p><p>Write requirements in terms of principals, actions, resources, and context. “Enterprise-grade security” is not a testable acceptance criterion. “A Warehouse A coordinator cannot retrieve or export Warehouse B records” is much closer.</p>
<h2 id="section-2">18.2 Integrate with the customer’s identity model</h2><p>Use the customer’s approved identity architecture and supported libraries rather than implementing a login protocol from scratch. OpenID Connect adds an identity layer on OAuth 2.0; its identity assertions serve a different purpose from an API’s access authorization. <a href="https://openid.net/developers/how-connect-works/" target="_blank" rel="noopener noreferrer">How OpenID Connect Works ↗</a></p><p>For the chosen flow, validate tokens according to the provider and library requirements, including issuer, intended audience, signature or introspection rules, expiry, and flow-specific protections. Do not treat merely decoding a token as validating it. Do not assume an ID token is a substitute for the access token expected by a resource server.</p><p>Agree on the source of warehouse membership and roles, how changes propagate, and what happens when a user leaves or changes teams. A signed token may contain old permissions until it expires; session lifetime, revocation, and authorization-cache behavior need an explicit design. “We use SSO” does not resolve these lifecycle questions.</p>
<h2 id="section-3">18.3 Start with an access matrix</h2><p>Describe the smallest set of operations each principal needs. Roles can organize capabilities, while attributes such as warehouse assignment constrain which records are in scope. Deny unrecognized roles, actions, or missing policy context by default. Validate access on every relevant server-side path. <a href="https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html" target="_blank" rel="noopener noreferrer">OWASP Authorization Cheat Sheet ↗</a></p><div class="table-wrap"><table><thead><tr><th>Principal</th><th>Allowed actions in this exercise</th><th>Resource boundary</th></tr></thead><tbody><tr><td>Coordinator</td><td>Read evidence; record a review.</td><td>Assigned warehouse only.</td></tr><tr><td>Auditor</td><td>Read evidence; export approved audit data.</td><td>Assigned warehouse only.</td></tr><tr><td>Ingestion service</td><td>Ingest source evidence.</td><td>Assigned warehouse only; no review or export.</td></tr></tbody></table></div><p>This is an illustrative policy, not a universal organizational role model. There is no implied all-access administrator. If Harbor needs cross-warehouse auditors or emergency access, define a separate authorized policy with scope, expiry, oversight, and audit requirements.</p><figure><img src="../../assets/images/chapter-18-flow.svg" alt="A validated principal and trusted resource attributes feed a server-side policy check. Browser hints are not trusted policy inputs."><figcaption>The resource’s warehouse comes from trusted server-side data, not a warehouse ID supplied by the browser.</figcaption></figure>

<h2 id="section-5">18.5 Follow the data beyond the main database</h2><p>Inventory the fields collected, their purpose, source, destinations, owners, retention, and deletion behavior. Include caches, queues, backups, logs, search indexes, downloaded exports, and support attachments. A deletion in the primary table may leave other copies subject to a different retention process.</p><p>Minimize collection before choosing encryption settings. If a pilot only needs shipment identifiers, timestamps, and exception categories, do not copy unrelated personal details simply because the source API returns them. Preserve enough evidence for the workflow while documenting what is intentionally excluded.</p><div class="lesson-panel"><h3>Data-flow inventory exercise</h3><p>Trace one evidence record from the OMS to the reviewer and then through an export or support investigation. Identify each copy, who can access it, how long it remains, and how deletion or correction propagates. Use fictional field names here.</p><label for="inventory18">Your data-flow inventory</label><textarea id="inventory18" data-save="field-18-inventory" rows="9" placeholder="Field / purpose / source&#10;Storage and transit locations&#10;Access owner and enforcement&#10;Retention, deletion, and backups&#10;Logging and support-copy limits&#10;Unresolved decisions"></textarea></div><p>Encryption in transit and at rest addresses specific threats, but does not stop an overprivileged application from reading data it is allowed to decrypt. Document key ownership, access, recovery, and operational responsibilities in the customer’s chosen platform.</p>
<h2 id="section-6">18.6 Treat secrets as a lifecycle</h2><p>Use approved secret storage and delivery mechanisms, with identities scoped to the required operations. Prefer supported short-lived workload credentials where appropriate. Separate production and development credentials, and avoid placing secrets in browser bundles, source control, screenshots, or support tickets.</p><p>Record who can issue, read, rotate, and revoke each credential. Rehearse rotation with the integration and confirm old credentials cease working as intended. If a secret is exposed, removing it from the latest file is insufficient: follow the incident process, revoke or rotate it, and examine its use and remaining copies. <a href="https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html" target="_blank" rel="noopener noreferrer">OWASP Secrets Management Cheat Sheet ↗</a></p><p>Do not share a human administrator’s credential with a service to unblock a demonstration. A demo should use an approved environment and identity whose privileges match its purpose. A temporary exception needs a real owner and expiration, not an informal promise to fix it later.</p>
<h2 id="section-7">18.7 Test denial as carefully as success</h2><p>A test suite that only confirms authorized users can read records cannot establish the isolation boundary. Pair positive tests with negative tests that vary one condition: principal, action, warehouse, account state, or permission revision. Include an authorized control case so a system that denies everything does not appear correct.</p><div class="table-wrap"><table><thead><tr><th>Test</th><th>Expected evidence</th></tr></thead><tbody><tr><td>Substitute another warehouse’s valid record ID</td><td>No unauthorized record or sensitive metadata is returned.</td></tr><tr><td>Call an export endpoint directly</td><td>The same resource boundary applies outside the UI.</td></tr><tr><td>Remove a warehouse assignment</td><td>Access changes within the documented propagation window.</td></tr><tr><td>Use an expired or wrong-audience token</td><td>Request fails according to the authentication contract.</td></tr><tr><td>Attempt a service action outside its scope</td><td>Operation is denied and appropriately observable.</td></tr><tr><td>Policy lookup is unavailable</td><td>The defined safe failure behavior applies; no accidental broad access.</td></tr></tbody></table></div><p>Test permission changes against caches and long-running sessions, not only new logins. Test object lookup and list filtering, because preventing direct access while leaking records in search is still a failure. Run authorized tests in the agreed environment and avoid exercising unrelated customer systems.</p>
<h2 id="section-8">18.8 Prepare a security review packet</h2><p>Give the reviewer a concise data-flow diagram, access matrix, identity integration description, credential lifecycle, audit design, test results, and unresolved risks. Distinguish implemented controls from planned work. State the version and environment tested, the responsible owner, and the decision needed.</p><p>Security review is collaborative engineering. Ask which requirement a requested control addresses and what evidence would satisfy it. If a control is infeasible within the pilot, propose a narrower scope or an approved alternative rather than claiming compliance. Product certification, contract commitments, and legal obligations require their appropriate owners; a local checklist does not establish them.</p><p>Keep the packet current when scope changes. Adding exports, cross-warehouse access, external notifications, or AI processing can introduce new data paths and permissions even if the original UI barely changes.</p>
<h2 id="section-9">18.9 Customer security-review workshop</h2><p><strong>Scenario:</strong> Harbor wants an export feature by Friday. The current UI filters records by warehouse, but the export worker uses a shared all-warehouse service credential. Audit logs include full payloads. The team says, “Only auditors can see the button, so it is safe.”</p><p>Spend 25–35 minutes writing a review response and a bounded implementation plan. Explain the enforcement gap, map the required policy through the background job, minimize logged data, and specify tests and owners.
