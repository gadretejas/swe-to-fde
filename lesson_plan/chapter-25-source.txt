<h2 id="section-1">25.1 What is an LLM?</h2><p>A large language model is a neural network trained to learn patterns in language and other data. For a typical text-generating model, the immediate task is to estimate which token could come next given the available context. Repeating that process produces an answer.</p><p>That simple description supports surprisingly broad abilities: rewriting, summarizing, extracting information, writing code, and working through problems. It does not mean the model consults an authoritative database for every sentence. A fluent answer can still contain an unsupported claim.</p><p>Think of a model as a learned capability inside a larger application. The application decides what information to provide, which tools are available, what the user may access, and how to display or validate the result. A model by itself does not automatically know your company's latest records.</p>
<h2 id="section-2">25.2 Tokens: the units a model processes</h2><p>Text is converted into tokens before the model processes it. A token may represent a word, part of a word, punctuation, or another text fragment. The exact split depends on the tokenizer; one word is not always one token, and different languages can use different numbers of tokens for comparable messages.</p><p>For intuition, imagine “Shipment delayed.” becoming a few small pieces that each have a numerical identifier. This is an illustration, not the output of a specific tokenizer. The identifier is a lookup code, not a measure of the word's meaning.</p><p><strong>Why it matters:</strong> token limits affect how much material you can provide and how long a response can be. Many hosted services also meter usage in tokens. Check a particular model's documentation before estimating a budget or promising that a large document will fit.</p>
<h2 id="section-3">25.3 Embeddings: numerical representations</h2><p>An embedding is a list of numbers used to represent an item, such as a token or a piece of text. Learned representations allow models to capture useful relationships. In a suitable text-embedding model, “late shipment” and “delivery delay” may be represented as similar even though their spelling differs.</p><p>Similarity is not proof of equivalence or truth. “The shipment arrived” and “The shipment did not arrive” share much of their language but have opposite operational implications. A useful representation still needs evaluation for the task.</p><p>There are two related ideas to keep separate: token embeddings inside a language model, and embeddings produced for application tasks such as document search. You do not automatically need a vector database just because a transformer uses embeddings internally. Chapter 27 will explain when retrieval infrastructure is useful.</p>
<h2 id="section-4">25.4 Attention and transformers</h2><p>A transformer is a neural-network architecture that uses attention to combine information across a sequence. Attention lets a token's representation draw on other relevant tokens in the available context. Position information helps the model distinguish ordering; attention is not the whole architecture, but it is a central part.</p><p>Consider “The crate would not fit in the van because it was too small.” Context suggests that “it” refers to the van. Change “small” to “large,” and the likely reference changes. Attention helps build context-sensitive representations, although this example is an intuition rather than a readout of a real model's internal reasoning.</p><p>Transformer layers repeatedly refine representations. Multiple attention heads can capture different relationships. You do not need to memorize matrices to use this idea: the interpretation of a token depends on surrounding context, not only its dictionary definition.</p><p>The original transformer used an encoder and a decoder. Variants use an encoder, a decoder, or both. Many text-generation LLMs use decoder-only architectures and generate using earlier tokens; not every transformer is a chatbot, and not every model has exactly the same architecture.</p><figure><img src="../../assets/images/chapter-25-flow.svg" alt="Text becomes tokens, then numerical representations processed by transformer layers, then next-token scores. <h2 id="section-5">25.5 Training versus inference</h2><div class="table-wrap"><table><thead><tr><th>Stage</th><th>What happens</th><th>Customer implication</th></tr></thead><tbody><tr><td>Pretraining</td><td>Learning algorithms adjust model parameters using large datasets and a training objective.</td><td>Broad capabilities come from learned patterns; coverage and correctness are not guaranteed.</td></tr><tr><td>Post-training</td><td>Additional training shapes behavior, such as instruction following. Fine-tuning is one approach; methods vary.</td><td>Models can differ in behavior even when their underlying architecture is similar.</td></tr><tr><td>Inference</td><td>An already-trained model processes context and generates a result.</td><td>Providing a document can affect this answer without retraining the model.</td></tr></tbody></table></div><p>A normal prompt does not itself update the model's weights. A product may separately retain conversation history, store memory, or use data in a later training process according to its settings and terms. Those are product and data-governance questions, not a consequence of attention.</p><p>A useful distinction is <strong>learned parameters versus supplied context</strong>. Parameters hold what training changed. Context is the material available for this generation, including instructions, conversation, documents, or tool results supplied by the application.</p>
<h2 id="section-6">25.6 How an answer is generated</h2><p>The model produces scores for possible next tokens. A decoding strategy chooses one, adds it to the sequence, and repeats until a stopping condition is reached. Sampling can produce different continuations; lower randomness does not turn a model into a factual verification system.</p><p>The context window limits how much tokenized material the model can work with in a request, subject to the provider's specific input and output limits. A longer window can accommodate more information, but it does not guarantee the model will use every important detail correctly.</p><p>Training may give the model general shipping knowledge. A prompt containing Harbor's current scan can supply case-specific evidence. Neither establishes that the model has independently verified the scan, checked permissions, or looked up a live shipment. The application must arrange those steps when needed.</p>
